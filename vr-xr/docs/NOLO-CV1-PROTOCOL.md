# NOLO CV1 新版固件 HID 报告格式

本文整理当前 NOLO CV1（现场 USB ID `0483:5750`）新版固件的 64 字节 HID
输入报告，供 Rust 直连后端、抓包分析和机械臂示教安全诊断使用。

本文只描述已经确认的字节行为，不把通信在线等同于基站光学跟踪有效。当前没有任何
已识别字段可以可靠表示基站电源状态；所有未知字段都不参与机器人安全决策。

这里的字节编号统一采用**解密后数组的零基下标**：字节 24 就是
`report[24]`，不是自然语言中的“第 24 个字节”。所有多字节整数均为小端序。

## 适用范围与依据

本文只适用于报告类型 `0x10`、`0x11` 的新版固件：

- `0x10`（16）：Controller 0 + HMD 数据。
- `0x11`（17）：Controller 1 + HMD 数据。

旧固件的 `0xa5`、`0xa6` 报告格式不同，不适用本文表格。

主要依据：

- [OpenHMD NOLO 包解码器](https://github.com/OpenHMD/OpenHMD/blob/master/src/drv_nolo/packet.c)
- [OpenHMD NOLO 报告分发代码](https://github.com/OpenHMD/OpenHMD/blob/master/src/drv_nolo/nolo.c)
- [OpenHMD NOLO 内部定义](https://github.com/OpenHMD/OpenHMD/blob/master/src/drv_nolo/nolo.h)
- [nolo-teleop 协议实现](https://github.com/j8swang/nolo-teleop/blob/main/src/nolo_teleop/protocol.py)
- [NOLO 官方 Windows Device SDK](https://github.com/NOLOVR/NoloDeviceSDK)
- [Christoph Haag 的 CV1 Pro 原始报告记录](https://gist.github.com/ChristophHaag/ed0f9c7ddc3f587953950355fcbd0104)
- 本项目的现场抓包、受控三轴动作、静止重力值和设备开关对照

这些资料并非完全独立：`nolo-teleop` 的协议解析明确以 OpenHMD 为来源，本项目 Rust
解码器又以二者为实现参考。因此，三份代码实现相同并不能算三次独立确认；
`nolo-teleop` 的真实抓包 fixture 和本项目的受控实机动作才是额外的实验依据。

官方 Device SDK 只公开了上层 API、示例和预编译服务端，没有公开 HID 报告结构，
因此可以证明厂商对外提供哪些能力，但不能直接为下表的未知偏移命名。CV1 Pro
记录使用不同产品和不同的首字节 `0x69`，不能直接套用到本机 CV1 的 `0x10/0x11`
报告；它只作为尾部字节行为的旁证。

本次复核的本地版本为：OpenHMD 固定基线 `85075b0c`（新版协议最初由提交 `d11e741`
引入），以及 `nolo-teleop` 提交
`5829d5f8010cbf91767c35709617c7e35ec9f3f9`。本项目给 OpenHMD 增加的 Fusion
补丁只修正单位、轴和姿态融合，不为未知字节提供额外定义。

OpenHMD 上游代码对新版固件部分 IMU 字段的名称存在历史错误。本文的 Controller
`7–12` 加速度、`13–18` 陀螺仪，以及 HMD `37–42` 陀螺仪、`49–54`
加速度，采用现场静止模长和受控动作确认后的含义。

## 加密范围

USB 原始报告为 64 字节：

- `report[0]` 不加密，是报告类型。
- `report[1..=60]` 按 15 个小端 `u32` 使用 BTEA/XXTEA 变体加密。
- `report[61..=63]` 不属于加密块。

密钥：

```text
875bcc51 a7637a66 50960967 f8536c51
```

下文所有偏移均指完成解密后的报告。

## 位置和 IMU 换算

控制器和 HMD Marker 的位置均为三个小端 `i16`：

```text
position_m = raw_i16 × 0.0001
```

控制器 IMU：

```text
acceleration_g = raw / 1024
angular_velocity_deg_s = raw × (2000 / 32768)
angular_velocity_rad_s = angular_velocity_deg_s × (π / 180)
```

HMD IMU：

```text
acceleration_g = raw / 16384
angular_velocity_deg_s = raw × (2000 / 32768)
angular_velocity_rad_s = angular_velocity_deg_s × (π / 180)
```

陀螺仪比例采用 `nolo-teleop` 的 signed `i16`、±2000 °/s 量程解释，即
`0.06103515625 °/s/count`（约 `0.0010652644 rad/s/count`）。这是当前主链路的
工作换算，不是 NOLO 公开协议给出的设备规格。项目没有转台或可靠角度参考，因此接受
该第三方实现数据，不再安排本地角速度尺度验证。冻结的 OpenHMD 历史补丁使用近似值
`0.001 rad/s/count`，当前 Rust 后端不再沿用。

当前实机验证后的控制器轴变换：

```text
accel = [ ax,  ay, -az]
gyro  = [-gx, -gy,  gz]
```

该变换发生在原始字段解码之后，不改变本表的字节布局。

## 未识别字段交叉分析

本节只整理能由公开实现或现有抓包重复验证的行为，不把“看起来像”
提升成协议事实。统计使用 `nolo-teleop` 的三份原始 fixture：

现场采样必须先分别确认基站、Head Marker 和手柄开机，再逐只唤醒并通过位置或 IMU
负载变化确认手柄真实更新。只收到报告类型而没有负载变化的采样视为无效，不进入结论。

| 抓包                  | 报告数 | 已知实验状态                           |
| --------------------- | -----: | -------------------------------------- |
| `glitchy_capture.bin` |   2400 | 两只控制器工作，含跟踪异常段           |
| `live_capture.bin`    |    475 | 控制器有效负载已冻结，HMD/中继仍在发包 |
| `tilt90_capture.bin`  |   1680 | 控制器进行 90° 倾斜动作                |

共计 4555 个报告，类型 `0x10` 和 `0x11` 均有覆盖。这些 fixture 是 `nolo-teleop`
对本文最有价值的部分；它的 `protocol.py` 本身并没有解析下面的未知字节。

2026-08-24 又在现场 CV1 上完成一次 12 秒受控采样：先分别确认并唤醒两只手柄，
再依次活动左、右手柄，基站和 Head Marker 保持不动。两种报告分别收到 1441、1440
包；Controller 0 有 1204 组不同 IMU 负载，Controller 1 有 1074 组，证明两只手柄
在采样窗口内都真实更新。未确认手柄开机状态的其他试采已经作废，不进入本文证据。

### 字节 22：控制器慢变量

观测值：

| 抓包                  | Controller 0 | Controller 1 |
| --------------------- | -----------: | -----------: |
| `glitchy_capture.bin` |           91 |           97 |
| `live_capture.bin`    |          255 |          255 |
| `tilt90_capture.bin`  |           55 |           58 |
| 2026-08-24 受控采样   |           35 |           93 |

每份抓包内该字节对同一控制器完全不变。历史工作抓包中两只手柄的数值接近，
但本次受控采样中的两只活跃手柄分别稳定为 `35` 和 `93`，说明数值也可以明显不同。

控制器停止有效上报的 `live_capture.bin` 中为
`255`。这些结果继续支持“有效范围类似 `0–100`、`255`
表示未知/不可用”的解释，但无法区分电量、无线链路质量、
传感器质量或其他慢变状态。

当前结论：**控制器相关慢变量，电量、链路质量或设备级配置值均只是候选**。
不得作为电量、在线状态或跟踪有效状态使用。最小确认实验必须先逐只唤醒手柄，
通过受控动作确认原始负载持续更新；然后在位置和基站不变时，
对同一手柄进行“充满电→持续放电→再充电”的长时间记录，并另做“与 HMD 逐渐拉远”的
信号对照。

### 字节 23：状态位与交替位的组合

已观测到的值只有 `0`、`2`、`3`、`6` 和 `7`：

- 控制器有效负载冻结时为 `0`。
- 三份 `nolo-teleop` fixture 中，正常工作段对同一 Controller 在 `6` 和 `7`
  之间逐包交替。
- `glitchy_capture.bin` 的短暂过渡段在 `2` 和 `3` 之间交替，然后进入 `6/7`。
- 2026-08-24 受控采样中，Controller 0 为 `6×721 + 7×720`，Controller 1 为
  `6×720 + 7×720`，与逐包交替完全吻合。

因此可以可靠地说，最低位 `bit 0` 是逐包交替的奇偶/相位信息；`bit 1` 和 `bit 2`
与控制器状态相关。但现有抓包不能把 `bit 1` 或 `bit 2` 进一步命名为“开机”
“光学跟踪有效”“基站可见”或“无线连接”。字节 23 目前只能整体保留，
不参与在线或跟踪有效判断。

### 字节 31–36：六字节保留候选

OpenHMD 在 HMD 位置后明确跳过这 6 字节。三份 `nolo-teleop` fixture 的 4555
个报告以及 2026-08-24 两只手柄已确认活跃的 2881 个受控报告中，该区间全部为
`00 00 00 00 00 00`。

当前结论：**当前 CV1 固件中的未使用/保留区候选**。这不能证明其他固件或 CV1 Pro
中也一定为填充；后端继续保留原始字节，不作为位置、速度或有效标志使用。

### 字节 43–48：HMD 三轴量候选

该区间恰好是 3 个小端 `i16`，位于 HMD gyro 和 accel 之间。OpenHMD
也是把它作为一个完整的 6 字节段跳过。解码为 `3×i16 LE` 时：

| 抓包                  | 值                   |
| --------------------- | -------------------- |
| `glitchy_capture.bin` | `[-895, -1396, 131]` |
| `live_capture.bin`    | `[0, 0, 0]`          |
| `tilt90_capture.bin`  | `[-895, -1396, 131]` |
| 2026-08-24 受控采样   | `[4279, 5776, 2463]` |

它在同一报告中对 Controller 0/1 完全相同，所以属于 HMD/中继侧，
而不属于当前手柄。从字段长度和 IMU 布局看，“磁力计原始量”是自然候选；
但活跃抓包中数千包完全无噪声、完全不更新，又更像校准常量或缓存值。

当前结论：**HMD 三轴量，磁力计/校准向量候选，不得输入姿态融合**。确认需要保持
HMD 位置不变而分别做绕三轴旋转，并另做磁铁靠近/远离对照。

### 字节 55–58：HMD 会话级四字节量

该区间在同一份抓包内始终不变，Controller 0/1 共享，但不同抓包的值不同：

| 抓包                  | 原始字节      | `2×i16 LE`      |
| --------------------- | ------------- | --------------- |
| `glitchy_capture.bin` | `c7 04 f6 43` | `[1223, 17398]` |
| `live_capture.bin`    | `72 d7 f4 ff` | `[-10382, -12]` |
| `tilt90_capture.bin`  | `81 fd f7 47` | `[-639, 18423]` |
| 2026-08-24 受控采样   | `b3 fd f7 30` | `[-589, 12535]` |

它不像持续时间戳、采样计数器或 IEEE-754 传感器浮点数；也不随当前控制器
动作变化。可能是 HMD 校准、设备状态、光学解算附加量或压缩编码值，
但目前没有哪一种获得支持。保持原始字节是唯一稳妥的做法。

### 字节 60–63：保留和未定义尾部

- `60–62` 在本地三份 fixture 的 4555 个报告以及 2026-08-24 的 2881 个受控报告中
  全部为零，其中 `61–63` 不在加密块内。
- `63` 在每份抓包中有 155–255 种取值，几乎每包都变，不是 `+1` 计数器。
- 2026-08-24 受控采样覆盖了 `63` 的全部 256 种取值，但 2880 次相邻转换中只有 9
  次恰好 `+1`，再次确认它不是递增序号。
- 对密文和明文分别检查逐字节 XOR、低 8 位求和及二补数求和，`63`
  都不符合这些常见简单校验。
- CV1 Pro 的公开原始报告也呈现 `62=0`、`63` 高频变化，但其首字节为
  `0x69`，因此只能作为尾部行为的弱旁证。

当前只把 `60–62` 记为保留/填充候选，把 `63` 记为不透明的高频尾字节。在得到厂商
定义或可重复相关性前，不把 `63` 解释成随机数、校验、时间戳或设备状态。

## 采样序号 24 / 59

这两个字段是本次协议分析中最可靠的新发现：

```text
report[24]：当前报告对应控制器的采样序号
report[59]：HMD/USB 中继采样序号
```

证据：

- 控制器正常工作时，`report[24]` 对该控制器严格逐包 `+1`。
- 控制器停止上报后，其 `report[24]` 固定不变。
- 同期 `report[59]` 仍严格 `+1`，说明 HMD/USB 中继仍在工作。
- `live_capture.bin` 中 Controller 0 的 `report[24]` 始终为 `82`，Controller 1
  始终为 `161`，而 `report[59]` 连续递增。

两个字段都是 `u8`，取值 `0–255`，随后从 `255` 回绕到 `0`。两个 Controller
报告交替出现，每类约 120 包/秒，所以各 Controller 的 `report[24]` 每约
`2.13` 秒回绕一次。HMD 字段存在于每个报告，合计约 240 份/秒。

2026-08-24 实时复核进一步确认：按 Controller 报告类型分别观察时，各自携带的
`report[59]` 序号流严格递增；但两类报告的序号相位不同，直接按 USB 到达顺序交错
比较会呈现一次前跳、一次后跳。这不影响“控制器停止后 HMD/中继仍继续采样”的既有
结论，但后端必须为 `report[16]`、`report[17]` 分别维护 HMD 序号状态，再把两路约
120 Hz 的新样本合并为约 240 Hz。序号 `255 → 0` 仍按正常回绕处理。

当前证据支持 Head Marker 的位置、IMU 字段和序号按约 240 Hz 随 USB 报告更新；
单只手柄仍是约 120 Hz。这里的频率是接收/采样序号频率，不是网页绘制帧率。

当前 Rust 后端不再用猜测的时间阈值判定序号失效。`unchanged_ms` 直接报告序号保持不变的
时长；实际 USB 打开/读取错误才把会话标记为离线。

`report[59]` 只说明 HMD/USB 中继仍在发包。基站关机时它仍可继续递增，因此字节
24/59 **不能判断基站电源状态**。

以下 Rust API 状态字段均由采样序号派生：`sample_sequence`、
`communication_fresh` 和 `hmd_relay_online`。
它们只表示采样新鲜度，不是光学 tracking valid/tracked 结论。没有协议依据的
`pose_usable`、`optical_tracking_valid`，以及迁移期的 `source_online` 和 `flags`
均未保留。手柄帧的 `sample_sequence` 取
`report[24]`，头部帧取 `report[59]`。

Rust API 的 `filtered_position` 是后端对 `report[1..=6]` 换算结果执行 One Euro

## 未知字段处理原则

对 `22–23`、`31–36`、`43–48`、`55–58`、`60–63`
暂不赋予电量、基站状态、质量标志或时间戳等名称。除非后续获得厂商定义，或者通过一次只改变一个物理条件的重复对照实验确认，否则后端只原样记录，不用于机械臂安全决策。
