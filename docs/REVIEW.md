## 重新标定等待反馈卡死（2026-09-13）

现场停在 `calibration-2`、已记录 1 个样本。20:30:24（Asia/Shanghai）主机内核记录
`usb 1-5-port3: disabled by hub (EMI?), re-enabling...`，随后 CH341 从 `ttyUSB0`
断开并在同一秒重新枚举为 `ttyUSB0`。EMI 是内核提示的可能原因，不能据此认定线材、
供电或用户拔线；没有证据表明是代码主动关闭 USB。执行节点读到 `Broken pipe`，
立即重开同一路径时收到 `No such file or directory`；设备随后恢复，但该次重连已失败。

软件缺陷是相机只等新电机反馈/TCP，不消费执行连接状态；网页 WebSocket 仍连接，
从而让串口故障表现为标定无限等待。修复增加同一执行状态的订阅和网页转发，
断连使活动标定失败并显示原始错误，已保存外参不变。重连沿用正式执行页，不自动续跑旧任务；
重新打开连接同时清除旧夹持调节状态，避免新反馈触发重放旧命令。不放松采样时间匹配，
不采用命令角度或历史 TCP 填充缺失数据，不增加猜测性的超时。

相机 25 项、视频模块 11 项、网关 6 项、执行节点 28 项和浏览器 2 项回归通过。
后续复审消除了顶部重复错误提示、补齐提示框下方间距，并改用源码内固定标定夹具，
避免界面回归依赖现场历史外参；前端 39 项单元测试、类型、Lint 与格式检查通过。
整套重启部署后，经真实网页测试无效串口、刷新、下拉与手动连接、重新标定：
连接失败立即显示明显错误，标定进入失败状态且没有生成运动请求，旧外参保持不变；
随后原路恢复 `ttyUSB0`，只读确认新反馈持续更新和 D415 保存结果逐字段一致。
该测试使用已断开的非设备路径，不重现实际 USB 电气故障，也没有运行新的真机九姿态运动。
复现入口为 `tools/diagnostics/verify-execution-serial-ui.mjs OUTPUT --calibration`。
真实 USB 瞬断诱因未能进一步确定，不把修复标定报错当作解决 USB 电气问题，
